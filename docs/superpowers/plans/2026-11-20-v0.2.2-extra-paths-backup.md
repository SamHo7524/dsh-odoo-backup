# dsh-odoo-backup v0.2.2 — 额外路径打包（extra paths）实施计划

> 目标版本 `0.2.2`；基线 `0.2.1`（`v0.2.1` 标签已被占用，基线含其 Electron 403 修复 `isLoopback`）。
> 起因：Odoo chatbot 依赖服务器上的知识库（`/root/Documents/Obsidian Vault`）与 hermes（`/root/.hermes`），
> 而当前插件的备份包只有 `dump.zip` / `addons` / `pydeps` / `odoo.conf` / `MANIFEST.json` 五项，
> 这两处**完全没有备份**（2026-11-20 核查，`/tmp/odoo-backup-20261114-111713.tar` 顶层仅 5 条目实证）。

---

## 0. 结论先行：这次要做成什么

一次备份 = 原有 Odoo 四项 + 用户按服务器配置的「额外路径」若干，**全部进同一个外层 tar、同一套加密、同一条传输与续传链路**。
不新增第二条备份通道，不新增第二份口令，不产生明文临时包。

范围边界（重要，别误解）：

- **做**：额外路径的打包、校验、记录、下载、加密、清理、UI 配置、Agent 回执、失败即拒。
- **不做**：额外路径的**自动恢复**（v0.2.3 独立提案，理由见 §1.6）。

---

## 1. 关键设计决策（自检结论）

### 1.1 打包形态：每路径一个 `tar.zst`，放进同一 workDir

沿用 `addons`/`pydeps` 既有形态：`<name>-<ts>.tar.zst`（远端无 zstd 时回退 `.tar.gz`），
落在 `/tmp/odoo-backup-<ts>/` 里，被既有外层 `tar -cf` 一并收走。

理由：外层 tar 已存在、加密与分片链路只认「一个包」，每路径独立成包让失败可定位（哪个路径炸了）、
体积可单列、未来手工恢复可直接 `tar -x` 单条。

**不**采用「把额外路径塞进已有 addons 包」：混在一起后单条恢复不可能，且 addons 包排除规则会污染。

### 1.2 体积现实（必须写进 UI 与文档）

2026-11-20 实测：

| 对象 | 全量 | 说明 |
|:--|--:|:--|
| `/root/Documents/Obsidian Vault` | 116,500,892 B ≈ 111 MiB | 中文文件名、含 `.git`/`.obsidian` |
| `/root/.hermes` | 6,488,786,133 B ≈ 6.04 GiB | `tools` 2.52G、`cache` 1.48G、`state-snapshots` 610M、`state.db` 619M、`node` 184M、`profiles` 161M、`installs` 144M、`lsp` 82M |
| `/root/.hermes` 排掉 `cache` 与 `*.lock` | 5,115,046,438 B ≈ 4.77 GiB | |
| 远端 `/`（含 `/tmp`）可用 | 24,691,154,944 B ≈ 23.0 GiB（已用 76%） | |

峰值约束：远端同时存在「额外 tar + 外层 tar」，即约 `2 × 额外原始字节`。全量 hermes 会让峰值逼近 12 GiB，
把可用空间从 23 GiB 压到 11 GiB。因此：

- 每路径独立压缩（`zstd -3`），压缩后远小于原始；
- 提供**推荐排除集**（见 1.3），把 hermes 收敛到「配置 + 状态」子集（约 850 MiB）；
- 打包前做**远端空间预检**，不足即拒（失败即拒，不静默降级）。

### 1.3 推荐排除集（写入 UI 提示与 README）

- vault：不排除（111 MiB 全量，`.git` 保留才有历史）。
- hermes「配置+状态」子集：`./cache`、`./state-snapshots`、`./installs`、`./node`、`./lsp`、`./tools`、`*.lock`、`*.sock`、`*.tmp`。
- hermes 全量：仅 `./cache`、`*.lock`、`*.sock`、`*.tmp`。

**`./` 前缀是顶层锚定**（2026-11-20 实测：`--exclude=./vault.key` 精确排除顶层 `vault.key`，而 `--exclude=vault` 不匹配任何成员）。
不带前缀的模式按「任意路径分量」匹配，`cache` 会连带排除 `tools/*/cache`——文档必须讲清，不能只丢一行示例。

### 1.4 路径含空格是本需求的一等公民

目标路径 `/root/Documents/Obsidian Vault` 含空格。因此：

- 参数一律经 `execRemote(..., { stdin })`（脚本走 argv base64，stdin 空闲——`lib/ssh.js:149-158` 实证），
  脚本内用 `IFS= read -r` 逐行读，所有使用点加双引号；
- 绝不用 `"$SRC"/*` 之类通配，改用 `-C "$SRC" ... -- .`；
- 已实测 `realpath -e '/root/Documents/Obsidian Vault'` 与 `tar -C '<含空格>'` 均正常。

### 1.5 安全与失败即拒（fail-closed）

| 风险 | 处理 |
|:--|:--|
| `name` 参与文件名 → 目录穿越（`../../etc/x`） | `^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$`；保留名 `addons/pydeps/conf/dump/manifest/odoo` 禁用；同服务器内重名即拒 |
| 路径注入 shell | 路径只经 stdin 传入 `read -r`，不拼命令；JS 侧拒绝非绝对路径、`/`、`..` 段、控制字符、超 512 字符 |
| 路径不存在/不可读 | **直接失败**（`EXTRA_RC=97/96`），绝不像 addons 那样记 `present:false` 后照样出包——用户显式配置的东西不能静默消失 |
| tar 读到活动文件（`file changed as we read it` → rc=1） | 接受 rc 0 与 1，把 stderr 摘要记进 manifest `warnings`；rc ≥ 2 失败 |
| 远端磁盘不足 | 打包前 `du -sb` + `df -B1` 预检，`required = extraBytes × 1.5 + dumpBytes × 2 + 512 MiB`，不足即拒 |
| 路径是 `/` 或系统关键目录 | 不做白名单（运维自己的机器），但 UI 与文档显式提示「额外路径下的内容会进备份包」 |

### 1.6 为什么本版不做额外路径的自动恢复

- 目标落点是 `/root/Documents`、`/root/.hermes`，后者是**常驻运行**的 hermes 主目录：
  自动解包会与运行中的进程抢文件，且 `state.db` 有 WAL，覆盖后可能直接损坏会话状态。
- 备份包内已记录足够信息（原始绝对路径 + 文件名 + 字节数 + SHA-256），手工恢复等价于一条命令：
  `tar -xzf <包内解出的 extra 包> -C <原路径>`。
- 自动恢复需独立设计「先备份现场 → 停服务 → 解包 → 校验 → 起服务 → 失败回滚」，属另一个破坏性操作面，
  必须走自己的 confirmToken 闸门，不能搭本次顺风车。

因此本版把「恢复说明」写进 README + Handoff，并在 manifest 里保留可恢复所需的一切。

### 1.7 兼容性

- MANIFEST `formatVersion` 由 `2.1` → `2.2`，新增**可选** `extras` 数组；旧包无 `extras` → 读取侧按「无额外路径」处理（`lib/package-meta.js:96-101` 只取 `source`，不受影响）。
- 新包被旧代码读取：旧代码只看自己认识的字段，多出的 `extras` 不影响。
- 续传：`findResumableBackup` 只看既有 manifest 与分片，额外路径不改变判定；续传分支**跳过**额外路径打包（本来就已完成）。
- 配置：旧配置无 `servers[].extraPaths` → 默认 `[]`。

### 1.8 自检发现的既有缺陷（本版顺带修，附证据）

1. **本地磁盘空间预检缺失**：设计规格 §16 要求 `≥ 2× totalBytes`，`lib/backup.js` 里没有实现。
   额外路径把包从 ~600 MiB 推到 1.5+ GiB 后，这一缺失会直接变成「组装到一半磁盘满」。
   → 本版在下载前补 `fs.statfs` 预检（`statfs` 不可用则跳过，不阻断）。
2. **`runBackup` 不可注入 `execRemote`**：`test/backup-failclosed.test.js` 传的 `_execRemote` 是**无效参数**（靠口令闸门先抛才看起来通过）。
   → 本版改为 `runBackup({ ..., deps = {} })`，`const exec = deps.execRemote ?? execRemote`。
3. **`servers` 是 `.volatile()` 活引用**：新字段必须同时出现在 schema 与 UI 读取路径，否则 `settings.update` 落盘时被剥掉（v0.1.15/0.1.16 已踩过两次）。
4. **`set -e` + `pipefail` + `| head` 会误杀脚本**：2026-11-20 探针实证（`tar | tar -tf | head -4` 触发 SIGPIPE，脚本提前退出，清理语句没跑）。
   → 打包脚本里禁止 `| head`，错误摘要用 `tail -c 400` 读文件。

### 2.3 脚本侧协议（`buildExtraPackScript` + `buildExtraPackStdin`）

stdin 顺序：`SRC` → `OUT` → `COMP`(`zstd`|`gzip`) → `NEX`（排除条数，十进制）→ N 行排除模式。

stdout 标记（每行一个，解析时容忍缺失）：

```
EXTRA_RC=<tar 退出码>          // 97 不存在 / 96 不可读 / 95 无 bash / 98 NEX 非法
EXTRA_ZRC=<压缩器退出码>
EXTRA_BYTES=<输出字节>
EXTRA_SHA256=<输出 sha256>
EXTRA_ERR=<stderr 摘要，单行>
```

脚本骨架（已在 toogel 实测通过同样形态：`PIPESTATUS=[0 0]`、`zstd -t` 通过、中文文件名无损）：

```bash
set -uo pipefail
[ -n "${BASH_VERSION:-}" ] || { echo "EXTRA_RC=95"; exit 0; }
IFS= read -r SRC; IFS= read -r OUT; IFS= read -r COMP; IFS= read -r NEX
case "$NEX" in ''|*[!0-9]*) echo "EXTRA_RC=98"; exit 0;; esac
EXCL=()
i=0
while [ "$i" -lt "$NEX" ]; do
  IFS= read -r line || break
  [ -n "$line" ] && EXCL+=("--exclude=$line")
  i=$((i+1))
done
[ -e "$SRC" ] || { echo "EXTRA_RC=97"; exit 0; }
[ -r "$SRC" ] || { echo "EXTRA_RC=96"; exit 0; }
ERRF="$OUT.err"
set +e
if [ ${#EXCL[@]} -eq 0 ]; then
  tar -C "$SRC" --numeric-owner -cpf - -- . 2>"$ERRF" | { if [ "$COMP" = gzip ]; then gzip -6 > "$OUT"; else zstd -3 -q -f -o "$OUT" -; fi; }
else
  tar -C "$SRC" --numeric-owner -cpf - "${EXCL[@]}" -- . 2>"$ERRF" | { if [ "$COMP" = gzip ]; then gzip -6 > "$OUT"; else zstd -3 -q -f -o "$OUT" -; fi; }
fi
st=("${PIPESTATUS[@]}")          # 必须在同一行取数组，否则被后续赋值重置（实测）
set -e
echo "EXTRA_RC=${st[0]}"
echo "EXTRA_ZRC=${st[1]:-1}"
echo "EXTRA_BYTES=$(stat -c %s "$OUT" 2>/dev/null || echo 0)"
echo "EXTRA_SHA256=$(sha256sum "$OUT" 2>/dev/null | cut -d' ' -f1)"
echo "EXTRA_ERR=$(tail -c 400 "$ERRF" 2>/dev/null | tr '\n' ' ')"
rm -f "$ERRF"
```

### 2.4 预检脚本协议（`buildExtraProbeScript`，只读）

每个路径输出 `PROBE=<path>\t<exists 0|1>\t<bytes>`，追加 `AVAIL=<df -B1 / 可用字节>`；
解析出 `entries[]` 与 `availableBytes`，供空间预算与「打包前先报错」使用。

### 2.5 进度阶段

`PHASES.backup` 内新增 `packing-extras`，取值夹在既有 `packing`（addons/pydeps）与 `compressing`（外层 tar）之间；
测试断言：阶段序列单调不减、0 ≤ percent ≤ 100、新阶段出现且位于两者之间。

## 5. 自审

**规格覆盖**：用户诉求（vault + hermes 进同一加密链路）→ §1.1/1.2/2.2/2.3 + Task 2；
安全（含空格路径、注入、穿越）→ §1.4/1.5 + Task 1；可观测（进度、回执）→ §2.5 + Task 5；
运维可用（体积、空间、恢复）→ §1.2/1.3/1.6 + Task 3/6/7。

**占位符检查**：无 TBD/「类似 Task N」；每个 Step 都有具体文件、断言或命令。

**类型一致性**：`extraPaths` 在 schema、UI、`normalizeExtras`、manifest `extras` 四处的字段名与顺序一致（name/path/exclude/maxBytes）；
manifest 用 `bytes`/`sha256`/`file`，与既有 `dump`/`addons` 条目的命名风格一致。

**风险登记**：
1. 全量 hermes 备份耗时可能 30+ 分钟（5 GiB 压缩 + 传输）→ 首轮验收用配置子集，全量单独一轮并挂后台。
2. `zstd -T0` 会吃多核；`-3` 单线程已够，保持默认不加 `-T0`（避免与 Odoo 抢 CPU）。
3. tar 读活动 `state.db`：接受 rc=1 + warning，文档明确「hermes 备份是尽力一致，不是事务一致」。

## 6. 执行方式

两种，取决于谁来做：

- **subagent-driven**：按 Task 逐一派发子代理，每个 Task 独立 RED→GREEN→变异验证，主代理只做集成与验收。
- **inline**：在本会话内按 Task 顺序执行（Task 1→7），每完成一个 Task 停下汇报一次。

默认建议 inline（Task 1/2 强耦合，拆给子代理会增加接口对齐成本）。
